Мультиплеер — задания для реализации

Задания подготовлены 14 ноября 2026 года. Реализация выполнена и проверена локально в ветках `codex/multiplayer`. Публикация не выполнялась.

Рабочие копии находятся рядом: `multiplayer/game` и `multiplayer/server`. В обоих репозиториях создана ветка `codex/multiplayer`. Исходная точка игры — версия `0.1.78`, коммит `534f066`; сервера — коммит `4cff8a8`. В эти коммиты перенесены текущие исходники и незакоммиченные изменения, имевшиеся до подготовки мультиплеера. Исходные каталоги `prototype`, `publish/GameOfThrows` и `game-archive-service` остаются на своих местах.

**Согласованное поведение**

- В комнате два стула: Север и Юг. Остальные участники — зрители.
- Каждый игрок выбирает свободную сторону и нажимает «Готов». Когда готовы оба игрока, сервер запускает партию один раз.
- Правила менять нельзя. Для первой реализации используется стандартная расстановка.
- Зрители могут войти во время партии и смотреть за игрой.
- Завершить партию может любой из двух игроков кнопкой «Завершить партию», без подтверждения соперника. Зрителям кнопка недоступна.
- После завершения оба стула освобождаются, готовность сбрасывается. Участники остаются в комнате и могут снова занять места.
- Отключение и бездействие сами по себе не завершают партию и не освобождают места.
- Если в комнате никого нет, включая зрителей, она удаляется.

**Принятые для проектирования уточнения**

Вошедший участник сначала становится зрителем; один участник может занять только один стул. До старта можно встать и снять готовность. Во время партии места закреплены за игроками. Возврат в том же браузере восстанавливает место.

Победитель определяется существующим движком: результат показывается, дальнейшие ходы блокируются. Освобождение стульев происходит только по кнопке. Нажатие до определения результата фиксируется как прерывание без победителя. Если оба игрока отключились, но зритель остался, комната и занятые места сохраняются; зритель не может завершить партию вместо игроков.

Сигнал присутствия отправляется каждые 20 секунд независимо от опроса состояния. Срок присутствия — 120 секунд для видимой вкладки и 600 секунд для скрытой. Запоздалый сигнал не сокращает уже выданный срок. Явный выход закрывает присутствие только текущей вкладки. Полностью приостановленный браузер не может продлевать присутствие: после истечения срока он считается отключённым. Если других участников нет, комната удаляется; если остался хотя бы зритель, места игроков сохраняются. Это срок восстановления связи, а не таймер партии.

**Контракт между сервером и клиентом**

Маршруты ниже реализованы. Транспорт — HTTPS-команды и опрос изменений примерно раз в секунду в активной вкладке. Присутствие учитывается отдельно от опроса снимков. Проверки задержки и нагрузки на целевом хостинге остаются частью подготовки к публикации.

| Маршрут | Назначение |
|---|---|
| `POST /api/rooms` | Создать комнату и присоединить создателя зрителем |
| `POST /api/rooms/:id/join` | Войти или восстановить участие |
| `GET /api/rooms/:id` | Получить снимок комнаты |
| `POST /api/rooms/:id/presence` | Подтвердить присутствие конкретной вкладки |
| `POST /api/rooms/:id/commands` | Занять стул, встать, изменить готовность, сделать ход или завершить партию |
| `POST /api/rooms/:id/leave` | Завершить присутствие конкретной вкладки; не освобождать место действующей партии |

Команда имеет единую оболочку:

```json
{
  "commandId": "uuid",
  "expectedRevision": 12,
  "matchId": "uuid-or-null",
  "type": "move",
  "payload": { "id": "piece-id", "to": { "q": 1, "r": 0 } }
}
```

Типы команд: `seat` с `{team: 0|1}`, `stand` с `{}`, `ready` с `{ready: boolean}`, `move` с `{id, to}`, `finish` с `{}`. Сервер проверяет личные полномочия независимо от значений команды. Для действий до старта `matchId` равен `null`; во время партии он обязателен. Старые команды не применяются к следующей партии.

Снимок содержит `roomId`, `revision`, `phase`, `matchId`, `config`, `state`, `seats`, `participants`, `self`, `lastAction`, `lastResult`, `serverTime` и `pollAfterMs`. `phase`: `waiting`, `playing`, `won`. Последнее значение означает, что движок определил результат, включая ничью, но игрок ещё не нажал кнопку завершения. `seats` — массив из двух мест; место содержит идентификатор участника и готовность либо `null`. Имена являются подписями, а не полномочиями.

После `finish`: `phase = waiting`, `matchId = null`, `state = null`, оба места пусты, результат предыдущей партии доступен через `lastResult`. Необходимые сведения для архива сохраняются до очистки текущей партии. Новая партия получает новый `matchId`.

Гостевой доступ восстанавливается личным секретом в браузере. В приглашение, снимки, ошибки и журналы этот секрет не попадает. Сервер хранит его хеш. Клиент создаёт 32 случайных байта через Web Crypto и сохраняет секрет транзакцией IndexedDB: вкладки одного источника используют одну идентичность, но отдельные идентификаторы присутствия. Код приглашения не даёт управлять чужой стороной.

Клиент предоставляет `create`, `join`, `claimSeat`, `stand`, `setReady`, `move`, `endMatch`, `leave`, `resync`, `stop`, подписку `onChange` и представление `view` со снимком, состоянием связи, ожидающей командой и доступными действиями. UI не обращается к HTTP напрямую.

**Задание серверному агенту**

1. Описать таблицы комнат, участников, присутствия вкладок, партий или их долговечных записей, событий и квитанций команд. Присутствие отделить от занятого стула. Имена участников ограничить по длине и передавать как обычный текст.
2. Переиспользовать `game/dist/engine.js` и `rules.js` из единого источника. Фиксировать правила при старте партии; обновление приложения не должно менять уже начатую игру. Способ исполнения предыдущих версий согласовать до выпуска.
3. Атомарно обрабатывать занятие стула, запуск, ход, завершение и удаление пустой комнаты. Состояние, событие и квитанция команды либо сохраняются вместе, либо не сохраняются. Одна лишь успешная SQL-транзакция не доказывает успешность условного обновления: нулевое число изменённых строк должно давать конфликт без лишних событий.
4. Повтор команды с тем же `commandId` и содержимым возвращает прежний результат. Тот же идентификатор с другим содержимым отклоняется. Несовпадение ожидаемой ревизии возвращает конфликт и актуальный снимок.
5. Проверять полномочия игрока, текущую партию, очередь и законность хода. Зритель не меняет партию. Оба игрока могут завершить её без второго подтверждения. Права проверяются на сервере, включая завершение после отключения и повторного подключения.
6. Удалять пустую комнату только после атомарной проверки отсутствия живых подключений. Одновременный вход должен исключать ошибочное удаление. Удаление комнаты не назначает победителя и не уничтожает уже сохранённую архивную запись партии.
7. Добавить ограничения размера и частоты запросов, проверку входных данных и разрешённых источников запросов. Существующие ограничения доступа к архиву не ослаблять.

Готовность серверной части подтверждают SQLite/API-тесты: гонка за один стул, один стул на участника, двойное «Готов», один старт, чужой ход, ход зрителя, повтор/конфликт/откат записи, двойное завершение, сохранение стульев при победе и отключении, поздний зритель, новая партия, последняя закрытая вкладка, возвращение одновременно с очисткой.

**Задание агенту сетевого клиента**

1. Отделить HTTP и хранение гостевой идентичности от жизненного цикла сессии. Одна идентичность восстанавливается после перезагрузки; каждой открытой вкладке нужен отдельный идентификатор присутствия.
2. При повторной отправке сохранять `commandId`, исходную ревизию и `matchId`. Не переносить конфликтный ход на новую позицию автоматически.
3. Применять снимки по возрастающей ревизии. Игнорировать поздние ответы комнаты, из которой пользователь уже вышел, и предыдущего подключения. После сомнительного результата запроса восстанавливать состояние с сервера.
4. Получать актуальную позицию при возвращении на вкладку. Не связывать остановку опроса скрытой вкладки с освобождением места. Поведение фонового присутствия проверить отдельно с серверным агентом.
5. Не заменять подтверждённую позицию локально рассчитанным ходом. `canMove` зависит от своего места, очереди, фазы, результата и состояния отправки.
6. Добавить префиксы к именам верхнего уровня: существующая сборка удаляет `import/export` и объединяет модули в один скрипт.

Готовность клиента подтверждают тесты с управляемыми ответами и временем: потерянный ответ, повтор команды, ответы не по порядку, смена комнаты, фокус вкладки, восстановление гостя, несколько вкладок и отсутствие секретов в публичных данных.

**Задание агенту интерфейса**

1. Добавить создание комнаты и вход по ссылке, два стула с именами, готовностью и состоянием связи, список или число зрителей. Действия: «Занять место», «Встать», «Готов», «Снять готовность», «Завершить партию», «Выйти из комнаты».
2. Подключить сессию к `humanCanMove`, `onCell`, `render` и показу результата. Зритель может изучать поле, но не отправлять ходы. Ход отображается как подтверждённый только после ответа сервера.
3. Оградить онлайн-режим от локальных обработчиков отмены, редактора, правил и новой игры. Не перезаписывать сохранённую локальную партию: сейчас `save()` вызывается при каждом `render()`.
4. Использовать существующие анимации для последовательных подтверждённых ходов. При восстановлении или пропуске ревизий отменять устаревшую анимацию и показывать актуальный снимок. Просмотр истории не должен откатывать серверное состояние.
5. Сохранить доступность элементов комнаты с клавиатуры. Проверить существующий перехват Tab и мобильную раскладку с `display: contents` у боковой панели.
6. Подключить клиентские модули в `build.mjs`. Сохранить обычную игру против бота и режим двух игроков на одном экране.

Готовность интерфейса подтверждают проверки прав игроков/зрителей, состояний стульев, готовности и завершения, сохранений, анимаций и запоздалых снимков. Затем — текущие тесты результатов, движения, навигации, настроек и бота; сборка и браузерная проверка на узком и широком экране.

**Порядок работ, использованный при реализации**

1. Основной агент проверяет включение общего движка в серверную сборку и доступность фонового удаления в текущем размещении Sites. Очистка только при следующем запросе не выполняет требование удаления пустой комнаты без новых посетителей.
2. Серверный и клиентский агенты согласуют идентичность гостя, формат снимка и сигналы присутствия. Сроки отсутствия проверяют в фоновых и приостановленных вкладках. Невозможно достоверно отличить закрытый браузер от полностью приостановленного без связи; выбранное поведение должно быть явно описано и проверено.
3. Перед изменением прав доступа проводится предварительная независимая проверка. Затем три агента реализуют свои области параллельно по общему контракту; UI и клиент используют одинаковые тестовые снимки.
4. Основной агент объединяет работу, добавляет серверную запись онлайн-партий в существующий архив без двойной записи из браузеров и проводит сквозную проверку. Комната удаляется отдельно от архивной истории.
5. Выполняются профильные тесты, сборки, проверка нескольких независимых браузерных сессий и итоговый аудит. Выпуск на прод не входит в эти задания.

Сквозной сценарий готовности: два игрока занимают разные стулья, оба готовы, третий участник смотрит; ходы совпадают у всех; перезагрузка возвращает игрока на его место; любой игрок завершает партию; оба стула свободны; другая пара начинает следующую игру; после ухода всех комната удаляется без нового входящего запроса.

**Локальный запуск и проверка**

Из каталога `multiplayer/server` выполните `npm run dev:multiplayer` и откройте `http://127.0.0.1:5188`. Сервер раздаёт соседний `game/dist`, обслуживает API и хранит отдельную SQLite-базу в `.room-data/development.sqlite`. Рабочие данные продакшена не используются. Нужен Node.js 22.13 или новее и установленные зависимости серверного проекта.

В меню выберите игру по ссылке, укажите имя и создайте комнату. Для двух игроков используйте разные браузеры или профили. Несколько вкладок одного источника разделяют гостевую идентичность; для локальной проверки можно открыть приглашение через `localhost:5188` во второй вкладке вместо `127.0.0.1:5188`.

Проверки игры: `npm test`, `npm run build`. Проверки сервера: `npm run test:rooms`, `npm run test:archive`, `npm run typecheck`, `npm run build`. Исторические исследовательские тесты игры используют материалы каталога `outputs` общего workspace; рядом с локальными рабочими копиями для них создана ссылка `multiplayer/outputs`.

Сервер использует закреплённую копию движка `0.1.78` из `shared-engine`; сборка проверяет её контрольные суммы и совпадение с исходниками игры, если соседний проект доступен. Старые версии движка нельзя заменять при обновлении: активные партии продолжают использовать записанную версию.

Онлайн-партии записываются в архив сервером в одной транзакции с ходом. Клиенты не могут дописывать эти записи через публичный API архива. Удаление комнаты сохраняет историю и не назначает победителя.

Локальная очистка пустых комнат запускается каждые 15 секунд. Для серверной сборки добавлены обработчик `scheduled` и cron раз в минуту. Перед будущей публикацией нужно подтвердить регистрацию cron в целевом размещении Sites, применить новые миграции и настроить адрес API в метатеге `game-room-endpoint`. Пустой адрес означает API на том же источнике, что и страница. Публикация и проверка расписания на проде в эту работу не входят.
